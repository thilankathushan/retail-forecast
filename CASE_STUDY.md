# Retail Forecast: making forecast evidence inspectable

The project asks a narrow question: **how well can last week's completed transaction history predict next week's observed positive product sales?** UCI Online Retail II provides over a million historical transaction rows, but no reliable inventory or availability history. Calling the target “demand” would imply knowledge the data cannot supply.

The first engineering decision was to make observation quality part of the model contract. Cancellations and non-product charges are excluded, negative units are tracked separately, missing customer IDs are retained, and repeated lines are flagged rather than automatically deleted. Incomplete weeks stay unknown. Zero sales require a documented complete-extract assumption. These choices make the target reproducible while exposing assumptions instead of hiding them in preprocessing.

The next decision was to make comparisons difficult to game. Dates were chosen before measuring performance; rolling origins use expanding past-only training. Every model scores the same origin-time eligible product-weeks. New products and sparse histories are reported as exclusions rather than silently dropped by the model that performs worst. Shifted features are shared between training and inference and tested against future-data perturbations.

A small scikit-learn global histogram tree was sufficient to improve the aggregate result without adding a new boosting stack. Two configurations kept development tuning bounded and practical on a laptop. On the frozen 13-week final evaluation, tree MAE was **18.95** and aggregate WAPE **59.71%**, versus **20.53 / 64.70%** for a trailing mean, across **59,395** common observations. That is about a 7.71% reduction in pooled absolute error, not a claim of business value or universal superiority. The tree still lost on 868 product MAEs.

Uncertainty was the clearest failure. Historical OOS residuals were normalized by each product's recent scale, but 80% intervals covered only **75.45%** overall and **55.39%** for medium-scale products. A 5,593-unit week was predicted at about 39 units. Most 95% misses were above the upper bound. I kept those failures in the report rather than recalibrating on the exposed final period and presenting it as an untouched test.

The application makes that evidence visible. A FastAPI service reads validated saved artifacts; Streamlit separates historical backtests, the unscored dataset-edge forecast and unsupported weeks beyond the dataset. A request never trains a model. Separate core, application and tracking environments prevent a UI dependency update from changing the frozen evaluation environment. Local MLflow traces configurations and data versions; a SQLite replay ledger makes repeated batch forecasts idempotent and delays error measurement until actuals are available.

The tradeoffs are explicit: four-week eligibility excludes cold starts; zero filling depends on extraction completeness; the API caches a roughly 59 MiB bundle; the demo uses product IDs instead of an unversioned catalog; monitoring arrival times are simulated; historical seasonal behavior may not transfer. A local read-only app and an application-only Docker image reduce deployment complexity, but do not constitute a production service.

Release preparation adds fixture-only CI, container configuration, data/model cards, startup and reproduction instructions, and actual screenshots. The application image built locally, both containers became healthy and HTTP smoke checks passed; both hosted CI jobs also passed after standalone publication. Original code is licensed under MIT; dataset attribution remains separate. Next work should use new evaluation data to investigate spike/segment uncertainty and a real source with measured arrival times—not retune and reuse the same holdout as fresh evidence.
